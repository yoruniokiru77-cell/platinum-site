# Platinum 店舗サイト・管理画面

静的HTMLとSupabaseを使う店舗サイトです。参考サイトの情報構成（バナー、最新情報、本日の出勤、ランキング、新人、ピックアップ、固定予約メニュー）を採用しています。

## ローカルで確認

Node.js 24系で `npm run dev`。公開ページは `http://127.0.0.1:4173/`、管理画面は `http://127.0.0.1:4173/admin.html` です。

管理画面の「画面を試す（デモ）」から編集できます。デモの下書きはブラウザー内に保存され、公開サイトへは反映されません。「プレビュー」は `?preview=1` 付きの画面でのみ、そのブラウザー内の下書きを表示します。

## 管理する内容

- セラピスト：写真アップロード、紹介文、公開／非公開、新人、SPECIAL、ピックアップ。
- 出勤：既存Supabaseから公開用API経由で取得（閲覧専用）。深夜2時は26:00。
- お知らせ：掲載日、カテゴリ、タイトル、本文、公開／非公開。
- バナー：テキストまたは画像、リンク。ランキング：任意の5名まで。
- 料金：コース、追加料金、税表記、キャンセル条件。
- 店舗：営業時間、受付表示、電話、Web予約、LINE、求人、SNS、アクセス。

セラピストを退店させる場合は削除ではなく非公開にします。プロフィールは固定IDで参照し、既存の `profile.html?idx=番号` も初期在籍者に限り維持します。

## 本番接続（初回のみ）

`assets/config.js` の `cmsEnabled` は true です。2026-10-05にHP用テーブル・関数と指定管理者の店舗権限を本番Supabaseへ適用しました。指定管理者のログイン・下書き保存・初回公開も確認済みです。公開設定の21名とお知らせ1件が公開され、非公開設定の19名は在籍ページに表示されません。

1. 接続先Supabaseプロジェクトを確認します。URL、公開anon key、店舗IDは `assets/config.js`。service-roleキーを置かないでください。
2. Supabase SQL Editorで `supabase/migrations/20261004_platinum_cms.sql` を実行します。既存 `shifts` とその権限は変更しません。
3. Supabase Authenticationで管理者ユーザーを用意し、メール確認を完了します。
4. SQL末尾の例にそのAuthユーザーUUIDを入れ、`platinum_admins` に対象店舗の管理者として登録します。ブラウザーから管理者権限を付与することはできません。
5. `cmsEnabled` を true にします。管理画面へログインし、初期データを確認して「下書き保存」→「プレビュー」→「公開する」。下書きは管理者限定、公開済みデータだけ匿名閲覧できます。
6. 別ブラウザー／未ログイン状態で公開内容を確認します。認証なし／別店舗ユーザーの書き込み拒否も確認してから運用します。

出勤の取得元は既存Supabaseの shifts に統一しました。登録・変更は既存シフト管理アプリで行います。旧CMSシフトデータは保存したまま、掲載には使いません。予約自体は既存の外部予約サービスで処理します。

本番CMSの取得失敗・未公開の場合は読み込みエラーを表示します。非公開にした在籍情報が初期データから再表示されないよう、本番では初期データへ戻しません。出勤の通信エラーは「出勤なし」と区別して表示します。初期データには旧サイトの掲載写真・紹介文を引き継いでいます。実際に掲載する内容は初回公開前に確認してください。

料金のキャンセル表示は、旧詳細説明の「施術開始1時間前以降50%、入店後全額」を移行しました。旧料金表の「当日一律半額」との不一致があったため、実運用ルールを店舗設定時に確認してください。税区分、駐車場、ランキングは未確定の情報を補っていません。

## 公開用シフトAPIと定期取得

構成：既存Supabase `shifts` → 公開専用RPC → HPの常駐Nodeサーバー（5分間隔）→ `GET /api/shifts` → HP。
ブラウザーから shifts テーブルを直接読みません。RPCは既存システムの保存形式（`[面接]` / `[特別]` 接頭辞、`is_dayoff_request`、`attendance_type`）に基づき除外します。通常出勤は `attendance_type` が `normal` または NULL のものに限定し、遅刻・早退を含むその他の区分も掲載しません。区分を追加した場合は公開条件の見直しが必要です。

### 初回設定

1. 既存Supabaseで `supabase/migrations/20261005_public_shifts.sql` を確認・適用します。店舗は神栖／PremiumのUUIDに固定。RPCは承認済み通常出勤の5項目だけを返します。テーブルの更新・既存RLSの変更はしません。
2. `.env.example` を `.env` にコピーし、`SHIFT_PUBLIC_API_KEY` に同プロジェクトの公開anon JWTキーを設定します。service-roleキーは不要です。
3. `SHIFT_DATE_BASIS` を必ず設定します。`calendar`：10/5 01:00 → 営業日10/4 25:00。`business`：既に営業日が保存されているため、10/5 01:00 → 営業日10/5 25:00。2026-10-05に店舗運用を確認済み：10/5 01:00は10/4 25:00として扱います。この店舗は `calendar` を指定します（設定例に反映済み）。未設定なら503になります。
4. Node.js 24系の常駐ホストで `npm start`。必要に応じて `HOST` / `PORT` を指定し、HTTPSリバースプロキシ経由で公開します。プロセスの再起動・常駐はホストのサービス管理機能で設定してください。
5. 管理画面の出勤一覧で連携IDを確認し、各セラピスト編集の「連携用セラピストID」へ入力して公開します。IDが未設定の場合だけ名前の完全一致にフォールバックします。

この変更には実環境へのSQL適用・本番ホスト設定は含まれていません。適用後、未承認／却下／欠勤／無断欠勤／休み申請／面接／特別予定が返らないことを既存管理画面と照合してください。

### HPのAPI仕様

`GET /api/shifts?from=2026-10-04&to=2026-10-10`（営業日、両端を含む最大31日間）

```json
{"ok":true,"from":"2026-10-04","to":"2026-10-10","timezone":"Asia/Tokyo","updated_at":"2026-10-04T03:00:00.000Z","shifts":[{"date":"2026-10-04","therapist_id":null,"therapist_name":"表示名","start_time":"12:00","end_time":"26:00"}]}
```

- 取得成功・出勤者なし：HTTP 200、`ok:true`、`shifts:[]`。
- 取得失敗・設定不足・応答異常：HTTP 503、`ok:false`、`error.code:SHIFT_FETCH_FAILED`。失敗時に空配列へ置換せず、過去の出勤を成功扱いで返しません。
- 不正な日付・逆順・31日超：HTTP 400、`error.code:INVALID_RANGE`。
- レスポンスは5項目を再構築し、上流APIに余分な項目があっても転送しません。電話・LINE・給与・内部メモ・ルーム情報を取得するSQLも含みません。

常駐サーバーは起動時に当日から7営業日分を取得し、5分ごとに先読み範囲と直近に要求された最大32範囲を更新します。初回要求・5分以上経過・直前の取得失敗時には同期取得します。キャッシュはメモリ内で、再起動時は取り直します。更新確認はページ再読み込み時に反映されます。

Vercelでは `api/refresh-shifts.js` をCronから5分ごとに実行し、公開用RPCをHPサーバー側で取得して `platinum_shift_cache` に保存します。`api/shifts.js` はこの永続キャッシュを読みます。直近の取得失敗・未作成・10分超の更新停止は503です。常駐Nodeホストの設定は代替方式として残しています。

## 採用する公開構成：GitHub → Vercel

GitHubの接続済みリポジトリは `yoruniokiru77-cell/platinum-site` です。Vercelの既存プロジェクト `sakabas-projects/platinum-site` を使用します（ユーザー選択済み）。同じリポジトリの `platinum-site-wny4` は今回の公開先ではありません。店舗HPは商用用途のためProプランが必要です（[Hobbyの利用条件](https://vercel.com/docs/plans/hobby)）。5分ごとのCronもPro対象です（[Cron制限](https://vercel.com/docs/cron-jobs/usage-and-pricing)）。この作業では有料プランの契約は行っていません。

1. Supabaseへ上記2つのSQLに加えて `supabase/migrations/20261006_shift_cache.sql` を適用します。永続キャッシュは匿名・管理画面ユーザーから読めず、Vercelサーバーのみ読み書きします。

3. VercelでGitHubリポジトリをインポートします。Framework PresetはOther、Root Directoryはルート、Node.jsは24.x。Build Commandは `npm run build:vercel`、Output Directoryは `public`（vercel.jsonに設定済み）。このビルドだけで公開用CMSが有効になり、ローカルのデモ設定は維持します。
4. Vercelのサーバー環境変数に以下を登録します。実データを使うPreviewにも登録する場合は、そのPreviewへのアクセスを限定してください。

| 名前 | 値・用途 |
|---|---|
| `SHIFT_PUBLIC_API_URL` | `.env.example` の公開RPC URL |
| `SHIFT_PUBLIC_API_KEY` | Supabase公開anonキー（シフト取得用） |
| `SHIFT_DATE_BASIS` | `calendar` |
| `SUPABASE_SERVICE_ROLE_KEY` | 同じSupabaseプロジェクトのサーバー専用キー。キャッシュ読み書きに使用。ブラウザー・Gitへ置かない |

5. デプロイ後、VercelのCron画面で `/api/refresh-shifts` の初回実行を行います。Cronは本番デプロイで5分ごとに動きます。初回取得前は出勤APIが503になる仕様です。認証なしで更新URLを開くと401になります。

7. `npm run build:vercel` の後に、環境変数を設定して `npm run preflight -- --vercel` で接続とキャッシュ鮮度を確認します。HTTPで公開ページ・API・管理ログインを検証してから独自ドメインを接続します。

本番Cronは今日から31営業日分を先読みします。キャッシュ範囲外の指定も最大31日間までHPサーバーから直接取得できますが、その場合は定期先読み対象ではありません。上流APIが失敗すると失敗状態を永続保存します。キャッシュ保存先自体が停止した場合は503、更新が途絶えた場合も10分で503となり、古い結果を無期限に成功表示しません。再デプロイや別インスタンスでも取得結果は維持されます。

GitHubへのPush・Vercelの作成／デプロイ・SupabaseへのSQL適用・管理者作成は、実行結果を確認するまで完了扱いにしません。SQL適用と公開API／匿名アクセス制限は確認済みです。Vercel上でのCron・HP管理画面ログイン・公開操作の検証は未完了です。

- 対象は神栖／プレミアム `https://estama.jp/shop/35702/bloglist/` の公開日記のみ。
